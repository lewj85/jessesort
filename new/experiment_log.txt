JESSESORT EXPERIMENT LOG
Last updated: 2026-08-09
Status: canonical source of truth for the current repository, active roadmap,
experiment decisions, timing deltas, and supporting evidence.

TIMING CONVENTION
- Unless stated otherwise, a negative candidate delta means faster than the
  baseline and a positive candidate delta means slower.
- Small effects require evidence proportional to their size: use the E066 canonical
  500-trials/seed x 2-seed paired benchmark for normal retain/revert decisions,
  and >=1000 trials/seed or a stronger phase-isolated causal harness for effects
  below roughly 1.5%.
- Historical artifact filenames remain as provenance references even though the
  compact repository no longer carries the old CSV collection. New benchmark raw
  data lives only in isolated, gitignored `results/run_*` directories.

1.1 BENCHMARK AND AUDIT STANDARD
- E066 supersedes the earlier 50-100-trial default because VM/host timing drift
  is large enough to obscure the sub-percent and low-single-digit effects now
  common in JesseSort optimization work.
- Canonical whole-sort benchmark defaults:
    * C++20, -O3, -march=native, -DNDEBUG; V7 uses AVX2 when the
      selected native target exposes it
    * n = 100,000 unless the experiment targets scale
    * 2 untimed warmups per workload
    * 500 measured trials per seed
    * 2 fixed seeds (1000 paired observations per workload)
    * 1000+ trials per seed for claims below roughly 1.5% unless a stronger
      phase-isolated causal harness is available
- Baseline/candidate/std::sort comparisons must use the same generated input in
  the same process whenever possible. Execution order rotates and reverses by
  trial to distribute cache/order effects. Correctness validation stays outside
  timed regions.
- Preserve raw paired timings. Report median, p25/p75, IQR, MAD, ratio of
  medians, and median paired ratio; do not silently trim outliers.
- Never use a saved std::sort median from another VM/session as a calibration
  constant. Absolute timings can move with host allocation, scheduler load,
  frequency behavior, and other VM effects. Historical absolute results are
  context only unless the old implementation is recompiled in the current run.
- For close A/B tests of header-only/template-heavy variations, prefer a
  layout-matched same-binary or phase-isolated causal harness. Separate copied
  implementations can alter inlining/code placement by several percent.
- Routine workload families: Random, Sorted, Reverse, Sorted+Noise(5%),
  Random%100, Alternating, Sawtooth, BlockSorted, OrganPipe, and Rotated. Use
  targeted distributions when a hypothesis concerns duplicates, routing, run
  shape, or another special property.
- Validate benchmark generators rather than trusting labels. Test non-integer
  types/custom comparators separately when correctness or genericity changes.
- Do not assume an optimization transfers between variations.

1.2 CURRENT MAINTAINED VARIATIONS

V1. ACTUAL PHYSICAL PILES
- Header: v1_actual_piles.h
- Namespace: jessesort::actual_piles
- Representation: vector-backed physical piles.
- Routing: equality preserves the current game.
- Merge policy: adjacent-pair merging with ordered/reverse-disjoint boundary fast paths and retained exponential-search galloping after seven consecutive wins in overlapping merges.
- Dedicated correctness/performance audit complete.

V2. SIMULATED BLUEPRINT
- Header: v2_simulated.h
- Namespace: jessesort::simulated
- Representation: sentinel-free value tails plus packed 32-bit blueprint.
- Flattening: sequential reconstruction into the merge buffer. Game grouping is
  always descending-game piles first, followed by ascending-game piles. The prior
  2-or-10-32 run-count selector was withdrawn as too specialized.
- Routing: equality preserves the current game.
- Pile-tail search / early insertion routing: the first-64 structure signal is
  retained. E065 superseded E054 after a historical-version recompilation showed
  that E054's apparent reversal was a code-layout/timing artifact. Sustained
  Random-like structure again dispatches to the direct no-hint continuation;
  structured/high-locality inputs retain the hinted/inline search.
- Merge policy: adjacent-pair baseline with adaptive ordered-boundary
  elimination for ordinary run sets; selected PowerSort-style alphabetic tree
  for n >= 32,768 when raw run sizes are sparse-dominant or compact-imbalanced.
  All overlapping two-run merges use retained 7-win exponential-search galloping
  from E035 unless the FINAL pile-density analysis confirms sustained Random-like
  structure, in which case E036's branchless merge is selected. E043 deliberately
  keeps this final merge decision separate from the earlier insertion decision.
- Dedicated correctness/performance and pile-tail-search audits complete.

V3. SIMULATED BLUEPRINT WITH IN-PLACE PERMUTATION FLATTENING
- Header: v3_inplace_simulated.h
- Namespace: jessesort::simulated_inplace_flatten
- Insertion matches V2. V3 then applies its own in-place physical run layout.
  E065 restored the first-64 Random-like no-hint continuation here together with
  V2 after E054's removal was falsified
  by current-environment recompilation of the preserved E045 implementation.
- Flattening: blueprint tags are converted to destination indices, then the
  array is permuted in place with cycle swaps.
- Merge policy: the same selected PowerSort-style alphabetic policy as V2
  for sparse-dominant or compact-imbalanced raw run sets; adjacent-pair merging
  remains the fallback. E038 now also retains V2's 64-element random router for
  the adjacent-pair path. Because V3 already shares V2's insertion engine, the
  probe metadata is collected with no second scan; sustained balanced high-pile
  random structure selects the branchless merge kernel for small trivially-copyable
  values.
- Retained as an experimental memory/reconstruction comparison; it is not the
  default simulated implementation.

V4. EARLY FREEZE + ONE LARGE DEFERRED OVERFLOW RUN
- Header: v4_single_overflow.h
- Namespace: jessesort::simulated_early_freeze_single_overflow
- Insertion routing: through the shared early-freeze core, E049 uses a separate
  first-64 classifier and one-time dispatch to hinted or no-hint insertion; the
  decision stays outside the long insertion loop.
- Merge routing: E040 retains the post-insertion blueprint-derived Random signal.
  A cheap late pile-density gate is evaluated first; sustained balanced high-pile
  Random uses the branchless adjacent merge kernel for eligible small trivially-
  copyable values.
- Freeze policy: 50% is the decision point. V4 uses a conservative power-of-two
  extension only when the combined pile count is 1 or in [4,32]; otherwise it
  freezes at 50%. Selected inputs continue ordinary pile creation to the strict
  next power-of-two cap.
- Overflow: one contiguous region sorted once with std::sort.
- Merge policy: selected PowerSort-style alphabetic scheduling when n >=
  32,768, there are at least 16 reconstructed runs, average raw run length is
  at least 25, and overflow is at most 10% of n; otherwise adjacent-pair.
- Delaying the large run until the final merge was tested and rejected.

V5. EARLY FREEZE + MULTIPLE DEFERRED-SORT OVERFLOW BANDS
- Header: v5_deferred_bands.h
- Namespace: jessesort::simulated_early_freeze
- Insertion routing: E049 classifies a separate first-64 prefix once, then dispatches
  to a fully hinted or fully no-hint early-freeze insertion specialization.
- Merge routing: the retained E039/E040 post-insertion blueprint/pile-density signal
  selects branchless merging for sustained high-pile Random structure on eligible
  small trivially-copyable values.
- Freeze policy: 50% is the decision point. V5 may continue ordinary pile
  creation to the strict next power-of-two combined pile cap when the broad
  selector activates: pile count <= 32, or n >= 32,768 and either pile count
  <= 4*sqrt(n) or the next cap is within 25% of the current count.
- Overflow: 32-element bands collected first and sorted after reconstruction.
- Merge policy: variation-specific dominant-first endpoint deferral when an odd
  run count begins with a first run at least 4x its immediate neighbor and
  larger than the final run; otherwise adjacent-pair baseline.
- This retained merge policy is not propagated to other variations.

V6. EARLY FREEZE + MULTIPLE LIVE-SORTED OVERFLOW BANDS
- Header: v6_live_bands.h
- Namespace: jessesort::simulated_early_freeze_live
- Insertion routing: through V5's shared early-freeze core, E049 uses the same
  one-time first-64 hinted/no-hint dispatch.
- Merge routing: E040 retains the density-first, post-insertion blueprint-derived
  router. Random-like inputs bypass the TimSort selector and use branchless adjacent
  merging; non-random inputs preserve the TimSort/adjacent policy unchanged.
- Freeze policy: 50% is the decision point. V6 uses the same broad selected
  power-of-two extension as V5 before entering the frozen/live-overflow phase.
- Overflow: each value is inserted live into the current sorted 32-element band.
- Merge policy: use a TimSort-style alphabetic run-stack tree only when the
  largest reconstructed run is at least 8x the mean run length; otherwise use
  the ordinary adjacent-pair baseline.
- Band size 32 is current. E010's 8-element choice was superseded by E028
  after E027 eliminated the organ-pipe overflow regime that had favored 8.

V7. AVX2 EXPERIMENTAL SIMULATED VARIATION
- Header: v7_avx2.h
- Namespace: jessesort::simulated_simd_v7
- Pipeline: V2-derived simulated insertion/reconstruction/merge.
- SIMD specialization: exact-eight int32 pile-tail lookup uses one AVX2 compare;
  broader sequential AVX2 scans and probe-gated continuation were rejected.
- E065 restored V2's first-64 Random-like no-hint continuation here as well.
- V7+ numbering is reserved for SIMD-specific experiments; V1-V6 remain the
  scalar/general algorithm variations.

1.2A VARIATION NUMBERING RESET (E050)

At E050 the variation numbering was deliberately normalized after an audit found
that V4/V5 names had drifted between discussion, documentation, and historical
records even though the implementation entry points themselves were correct.
From E050 onward the canonical order is:
  V1 = actual physical piles
  V2 = ordinary simulated blueprint
  V3 = simulated blueprint with in-place permutation flattening
  V4 = early freeze + one large deferred overflow run
  V5 = early freeze + multiple deferred-sort 32-element overflow bands
  V6 = early freeze + multiple live-sorted 32-element overflow bands
Historical prose in this log has been translated to this canonical numbering by
implementation identity. Raw historical artifact filenames are preserved for
provenance, so pre-E050 filenames containing V4 or V5 may still use the old
V4=deferred-bands / V5=single-overflow labels. When a filename and this log
disagree, use the implementation/namespace recorded by the experiment as ground
truth.

1.3 CURRENT SHARED ENGINEERING DECISIONS
- Numeric sentinels removed from maintained implementations.
- Copyable, movable, non-default-constructible values supported.
- Move-only values remain unsupported because pile-tail mirrors are copied.
- Comparator must provide a strict weak ordering. Inputs containing NaNs require
  an explicit total-order comparator such as NaN-last.
- Conventional even-sample median retained.
- JesseSort/std::sort execution order alternates or rotates by trial.
- Random%100 samples uniformly from [0,99].
- Sorted+Noise uses 5% independent random replacements.
- Misleading jitter benchmark removed.
- BlockSorted safely handles a partial final block.
- Routine canonical benchmarking stays at n=100,000; scale-specific 1M
  tests are run explicitly when an experiment targets scale.

1.4 CURRENT BENCHMARK ARTIFACT POLICY
- `benchmark.cpp` is the single canonical whole-sort benchmark in the compact
  repository.
- No benchmark result snapshot is tracked at repository top level. Each
  invocation writes an isolated, gitignored `results/run_*` directory containing
  `benchmark_results.csv`, `benchmark_trials.csv`, `benchmark_metadata.txt`, and
  `benchmark_progress.txt`.
- Performance decisions use same-run std::sort measurements and paired raw
  observations. Historical CSV collections were removed from the compact repo;
  their decision-relevant findings remain in this experiment log.

TOP-TIER PRINCIPLE
------------------
Optimize whole-sort cost, and preserve phase-local causal measurement. Routing
should be decided from cheap early/final metadata and dispatched outside hot loops
whenever possible. E065 restored the validated E043 early-Random no-hint
continuation in V2/V3/V7 after E054 was falsified; preserve that route unless new
causal evidence supersedes it. Do not rerun E056's rejected V1 scalar hint-miss
permutations unchanged.

1. V2 FINAL-LAYOUT / MERGE OPTIMIZATION — HIGHEST ACTIVE ALGORITHM PRIORITY
   - Continue from E044/E045/E053/E063 production state: 4x branchless unroll,
     run-shape gallop trigger routing, size-aware global branchless gate, and the
     retained 1.5x pair-imbalance galloping route in the measured mid-density band.
   - Add genuinely new final-layout signals: game balance, run-count/length
     distribution, largest-run dominance, duplicate saturation, ordered/reverse-
     disjoint boundaries, and predicted gallop streak potential.
   - Test materially different kernels/schedulers only: hybrid branchless/gallop,
     richer boundary elision, direct handling of very small run sets, or new
     scheduler routing from final structure. Do not rerun the E044 unroll sweep,
     E045 5-vs-7 sweep, or E063 1.5x rule unchanged.
   - SIMD merge kernels belong to V7+ experimental variations, not silent V2
     patches.
   - Use merge-only/layout-matched harnesses when whole-sort code layout obscures
     causality; validate retained routes end-to-end afterward.

2. V1 SEARCH / INSERTION — ONLY MATERIALLY DIFFERENT KERNELS REMAIN
   - Preserve E046 low-locality Random direct bit-walk and E047 high-locality
     exact previous-pile hint -> ordinary binary fallback.
   - E056 closed adjacent checks, direction-restricted scalar search, and
     bit-walk-on-hint-miss. Do not rerun those scalar permutations unchanged.
   - Remaining useful work is a genuinely different pile-search kernel or data
     layout (SIMD/small-pile lookup, Eytzinger-like physical-tail layout if it can
     be maintained cheaply, hardware-guided branch/cache work).
   - A successful exact hint should bypass any search kernel entirely; only misses
     should pay the new lookup cost.

3. SIMD VARIATIONS V7+ — EARLY-FREEZE / CHUNKED INSERTION TRACK
   - V7 remains the AVX2 exact-eight-tail proof of concept. E058 rejected a broad
     post-probe AVX2 continuation route as a robust whole-sort optimization.
   - Next AVX2 experiments: freeze/cap each game at 8 or 16 piles during the early
     probe and spill additional values to deferred overflow; then test extending
     this into SIMD-friendly insertion chunks whose active bases stay within the
     efficient SIMD width.
   - Add AVX-512 counterparts (natural exact-16 int32 lookup, early freeze, and
     chunked insertion) before attempting multi-register linear scans.
   - Compare SIMD early-freeze/chunked designs against V2/V3 and scalar V4-V6 with
     all spill/reconstruction/merge costs charged.

4. MULTI-REGIME ROUTER EXPANSION
   - E052/E053 established that duplicate-heavy and sustained high-entropy final
     layouts need different merge treatment. E054's separate duplicate-classifier
     subtest found no additional duplicate-specific insertion policy worth routing
     to; E054's removal of the Random no-hint route was later superseded by E065.
   - Continue only when a new kernel/policy creates a meaningful choice. Candidate
     early regimes include high locality, persistent few-pile structure, strong
     game imbalance, and ambiguous/general fallback. Candidate final regimes
     include duplicate saturation, sustained high entropy, few-run compatibility,
     strong run imbalance, and gallop-friendly layouts.
   - Record early->final route transition matrices and validate thresholds across
     size, cardinality, distributions, and held-out seeds.

5. PIECEWISE-MONOTONE NATURAL-RUN ROUTE
   - E055 rejected generic structured run scanning but found large potential for
     OrganPipe/Rotated-like layouts where long monotone regions stay in one pile.
   - Revisit only as a narrow route with cheap evidence (for example a very long
     initial monotone prefix plus a compatible continuation boundary). Avoid
     rescanning overlapping runs such as Sawtooth.
   - Measure searches avoided, bulk-assignment/merge traffic, run-layout changes,
     and final merge cost with false-positive overhead charged.

6. V5 DYNAMIC OVERFLOW / MERGE-TREE BALANCING — HIGH POTENTIAL, PAUSED
   - Fixed-size response surface is characterized (E059); 32 remains a strong
     general baseline. E060 rejected naive global adaptive sizing and local pair
     equalization. E062 rejected power-of-two run-count shaping and global
     PowerSort.
   - Keep the central idea: use deferred overflow as a DYNAMIC MERGE-TREE BALANCING
     RESOURCE. Future work must jointly choose nonuniform overflow partitioning and
     merge scheduler from actual post-insertion structure, with a cost model for
     sorting/inserting overflow versus merge traffic/depth/boundary elimination.
   - Resume later with planner/scheduler co-optimization, not more fixed band-size
     sweeps or unconditional local equalization.

7. CROSS-PHASE / FREEZE ENGINEERING — SECONDARY
   - Use insertion choices to shape final runs only when measured merge savings can
     repay insertion cost.
   - Frozen-base Eytzinger/compact-search ideas remain candidates for V4-V6.
   - Add low-trial 1M phase instrumentation before reopening static freeze-point or
     overflow policies. Do not rerun old fixed-threshold sweeps unchanged.
   - Propagate future successful routing independently. E065 restored the
     early-Random no-hint continuation in V2/V3/V7; V4-V6 retain their separate
     out-of-loop early-freeze hint-routing path from E049.

8. CODE CONSOLIDATION / MODULARIZATION — E064 ARCHITECTURE PLAN, NO REFACTOR YET
   - V7 is ~97% line-similar to V2 and should become a thin policy specialization,
     not a maintained full fork.
   - Extract shared simulated primitives in stages: packed tags/result types,
     pile-search kernels/policies, ordinary simulated insertion engine,
     reconstruction/run-layout helpers, merge kernels/schedulers, and routing
     metadata/decisions.
   - Preserve V3's good composition pattern: share V2 insertion and replace only
     flattening/reconstruction.
   - Keep V4/V5/V6 overflow behavior as separate thin strategies over a shared
     early-freeze insertion/base-layout core; do not create a giant runtime-
     switched freeze function.
   - Consolidate V1 with the simulated family only at genuinely shared low-level
     seams (search primitives and contiguous merge kernels). Its physical pile
     storage/insertion orchestration should remain distinct.
   - Prefer compile-time policy templates and one-time dispatch outside hot loops;
     avoid virtual calls/std::function/per-element runtime policy branches.
   - Before each extraction, create equivalence tests and same-binary performance
     checks because prior loop/code-layout changes have moved timings materially.
   - The E064 record below contains the proposed module boundaries and
     migration order; the standalone audit file was intentionally omitted from this
     compact repository.

9. AUTHORITATIVE PERFORMANCE CONSOLIDATION

   - Periodically re-profile phases because routing/refactoring can move the

Status: retained only for V2 under a run-shape selector.

- Can a PowerSort-style alphabetic merge tree reduce V2 merge traffic without
  imposing tree-construction and irregular-materialization overhead on balanced
  random run sets?

Pure PowerSort characterization:
- Preserved run order and adjacency.
- Assigned powers from adjacent normalized run midpoints.
- Built an alphabetic merge tree and chose root-buffer parity to minimize leaf
  copies.
- At 100k, pure PowerSort was about 4.09% slower on Random but 7.04% faster on
  Sorted+Noise(5%), 4.58% faster on Sawtooth, and 4.57% faster on BlockSorted.

- Require n >= 32,768.
- Sparse-dominant branch:
    * raw average run length >= 35;
    * largest run >= 8 * mean run length.
- Compact-imbalanced branch:
    * 16 <= raw run count <= 128;
    * largest run >= 2.25 * mean run length.
- All other inputs use the existing adjacent-pair scheduler.

- BlockSorted +0.80%, OrganPipe +0.34%, Rotated +1.02%.

E022 — SINGLE-OVERFLOW POWERSORT MERGE SCHEDULER
Status: retained only for V4 under a single-overflow-specific selector.

Question:
- Can a PowerSort-style alphabetic tree exploit the many normal runs plus one
  terminal overflow run without imposing the pure scheduler's overhead on
  random and dense-noise inputs?

Pure PowerSort characterization:
- At 100k, Random was +1.72%, Sorted+Noise(5%) -10.31%, Random%100
  -1.57%, BlockSorted +2.36%, and the remaining routine workloads were within
  about +/-2%.
- Targeted 100k noise 1/2/5/10/20% was -15.34%, -8.49%, -11.56%,
  -4.29%, and +2.84%, respectively.
- Targeted 1M noise 1/2/5/10/20% was -21.87%, -19.81%, -15.35%,
  -10.38%, and +3.22%, respectively.
- Therefore unconditional PowerSort was rejected.

Run-shape finding:
- Random 100k typically places about 15-16% of the input in the one overflow
  run despite having long average runs.
- Noise 1-10% generally has a smaller overflow region and average raw run
  length of at least about 29.
- Noise 20% has average raw run length around 16 and does not amortize the
  PowerSort tree path.

Retained V4 selector:
- Require n >= 32,768.
- Require at least 16 reconstructed runs.
- Require average raw run length >= 25.
- Require overflowCount <= 10% of n.
- Otherwise retain adjacent-pair merging.

Exact-header median 100k change across three independent interleaved
100-trial processes:
- Random -0.36%, Sorted+Noise(5%) -9.76%, Random%100 -2.26%.
- Alternating +0.76%, Sawtooth -0.04%, BlockSorted +0.53%.
- OrganPipe +0.57%, Rotated +1.34%; all treated as neutral.

- Noise 2%: -9.81% at 100k, -22.24% at 1M.
- Noise 5%: -10.53% at 100k, -13.13% at 1M.
- Noise 10%: -3.83% at 100k, -10.73% at 1M.
- Noise 20%: +0.34% at 100k, -0.01% at 1M; fallback/neutral.

Decision:
- Retain only in jessesort::simulated_early_freeze_single_overflow::sort.
- Do not reuse this selector in other variants without direct tests.

E027 — POWER-OF-TWO FREEZE TARGETING
Status: retained variant-specifically for V5, V4, and V6.

Question:
- Can early-freeze pile creation stop at a useful power-of-two boundary so the
  reconstructed run set is cheaper to merge, without creating enough extra
  overflow work to erase the benefit?

Rejected interpretations:
- Rounding the 50%-point normal pile count down to the nearest power of two was
  rejected. It froze too early, generated substantially more overflow, and often
  left merge depth unchanged or worse.
- Oracle total-run targeting was used as a structural upper-bound experiment.
  Even when cap selection was free, reducing nominal merge depth alone was not
  sufficient: extra overflow work could dominate. This oracle timing was not
  used as production decision evidence because early prototypes did not preserve
  every production fast path.

Retained interpretation:
- Keep 50% as a decision point rather than an unconditional freeze.
- Measure the combined normal pile count p at that point. If a variant-specific
  selector activates, continue ordinary (unfrozen) pile creation until the
  combined pile count reaches the strict next power of two, 2^k > p, or the
  input ends. Only then enter the normal frozen overflow phase.
- V5/V6 broad selector:
    * always extend when p <= 32;
    * otherwise require n >= 32,768 and either p <= 4*sqrt(n), or the strict
      next power-of-two cap is no more than 1.25*p.
- V4 conservative selector:
    * extend only when p == 1 or 4 <= p <= 32;
    * keep the 50% freeze for p == 2, p == 3, and larger pile sets.
- The direct simulation helper retains `FreezePolicy::fixed_half` as its default
  for compatibility and controlled tests; production V5-V6 opt into their
  selected policies explicitly.

Direct 100k A/B evidence:
- Exact production-like candidate versus untouched fixed-half baseline, identical
  inputs, interleaved order, 40 trials per process, three independent processes.
- Median candidate deltas:

                    V5 deferred32   V4 single run   V6 live8
  Random               -4.02%          +0.22%         -4.36%
  Noise 5%             -0.75%          -2.17%         -2.80%
  Random%100           +2.99%          +1.63%         +4.09%
  Alternating          +0.65%          -1.70%         -0.47%
  Sawtooth             -6.39%         -32.44%         -3.62%
  BlockSorted          -7.15%         -24.24%         -2.89%
  OrganPipe           -34.37%         -29.95%        -50.78%
  Rotated              -1.79%          -4.91%         +2.63%

Scale checks:
- At 10k, the retained policies preserved the structured gains; V5/V6 Random%100
  did not regress materially in that run.
- At 1M with a lower-trial harness, the structured gains persisted, including
  Sawtooth, BlockSorted, and OrganPipe. V5/V6 Random%100 regressed about 5.8%
  and 7.0%, respectively. This duplicate-heavy tradeoff is recorded explicitly
  rather than hidden; the general-input gains were judged more important.

Structural examples at 100k:
- V5 Random: 607 -> 866 normal piles, overflow 16,389 -> 0, total runs
  1,120 -> 866, nominal depth 11 -> 10.
- V5 Sawtooth: 11 -> 16 piles, overflow 49,890 -> 24,920, runs 1,571 -> 795,
  depth 11 -> 10.
- V5 BlockSorted: 9 -> 12 piles, overflow 10,002 -> 0, runs 322 -> 12,
  depth 9 -> 4.
- OrganPipe: all three variants move from one normal pile plus 49,999 overflow
  values to two normal piles and zero overflow. V5 runs fall 1,564 -> 2 and V6
  runs 6,251 -> 2.
- V4 Sawtooth improves about 32% even though its run count rises 12 -> 17 and
  nominal depth rises 4 -> 5. V4 OrganPipe improves about 30% while nominal
  depth remains 1. These cases prove that overflow sorting cost can matter more
  than simply minimizing merge-pass count.

Decision:
- Retain the broad selected power-of-two extension in V5 and V6.
- Retain the conservative low-pile extension in V4.
- Do not use nearest-below power-of-two pile caps.
- Do not optimize only for nominal merge depth; future freeze work must measure
  overflow volume/cost and actual merge traffic together.
- Keep the Random%100 regression visible as a known duplicate-heavy tradeoff.

Validation:
- Full maintained release-mode test suite passed after integration.
- Dedicated selector true/false tests and an OrganPipe structural regression
  test cover the new policy.
- Targeted Clang ASan/UBSan runs covered early-freeze boundary, single-overflow,
  live-overflow, and generic-type paths without reported errors.
- A post-change controlled six-variant benchmark was saved as the new
  authoritative snapshot.

E028 — RANDOM-INPUT LINEAGE AUDIT
Status: retained one V6 production change; V1/V2 unchanged.

Question:
- Have the accumulated optimizations degraded random-input performance relative
  to each variant's own original ancestor, and can any real regression be
  recovered without sacrificing structured-input performance?

Methodology correction:
- An earlier related-lineage benchmark placed multiple renamed, template-heavy
  header implementations in the same translation unit. Small multi-percent
  deltas changed with code layout and were not reliable regression evidence.
- Final lineage comparisons compile current and original wrappers in separate
  translation units, then interleave calls on identical random arrays. This is
  now the required method for close header/template A/B comparisons.
- Original lineage mapping:
    * V1 current actual piles -> original actual_piles.hpp;
    * V2 current simulated -> original simulated.hpp;
    * V6 current live early-freeze -> original simulated_early_freeze.hpp.
  V3/V5/V4 did not have exact original counterparts.

Final random lineage medians (current / original; negative is faster):
                     10k        100k        1M
  V1 actual         -0.319%     -0.038%     +0.467%
  V2 simulated      -7.890%    -10.167%    -12.117%
  V6 live32         -0.969%     -5.682%     -4.968%

Interpretation:
- V1 is effectively unchanged from its original random performance. The earlier
  apparent ~3% regression was a same-translation-unit code-layout artifact.
- V2 is materially faster than its original random implementation, with the gain
  increasing from about 8% at 10k to about 12% at 1M.
- V6 becomes faster than its original live early-freeze ancestor after restoring
  32-element live bands under the current E027 freeze policy.

V6 live-band re-evaluation:
- E010 previously retained 8-element live bands because, under the old freeze
  regime, they reduced organ-pipe insertion shifts by about 20-24%.
- E027 later changes organ-pipe to two normal piles and zero overflow, removing
  the workload that justified the smaller live bands.
- Under the current E027 freeze policy, 32 versus 8 live bands changes random:
    * 10k:  -0.689%
    * 100k: -1.732%
    * 1M:   -6.000%
- At 100k, all other routine-workload median changes were within about +/-1%:
    * Noise5 -0.21%, Random100 +0.57%, Alternating +0.86%, Sawtooth +0.94%,
      Block +0.42%, OrganPipe -0.01%, Rotated +0.23%.
- Decision: restore V6 live band size to 32. This supersedes E010's current-band
  decision but does not invalidate E010's historical pre-E027 measurement.

Rejected random-input candidates:
- V1 one-comparison routing recovered a narrow random gain in isolated builds,
  but produced structured/code-generation regressions and changed duplicate
  routing behavior in its simplest form. Rejected.
- V1 scalar previous-value and source-lookahead routing paths did not provide a
  safe, repeatable general gain. Rejected.
- A more permissive V6 random-friendly freeze/small-n policy recovered several
  percent on random inputs, but production-like builds showed a repeatable
  roughly 5% penalty on the already-fast organ-pipe path from added hot-code
  complexity/front-end effects. Rejected for now; revisit only with a cleaner
  compile-time/specialized policy implementation.

Decision:
- Retain no V1 change; current random performance is neutral versus original.
- Retain no V2 change; current V2 is already substantially faster than original

- Restore V6 live overflow bands from 8 to 32 elements.
- Treat separate-translation-unit A/B construction as part of benchmark

E029 — V2 DESCENDING-GAME-FIRST RECONSTRUCTION ORDER
Status: unconditional descending-first retained for V2; specialized selector withdrawn.

Question:
- Does placing descending-game piles before ascending-game piles improve the
  flattened run sequence enough to reduce merge work?

Benchmark method:
- V2 only. Shared-code runtime-policy A/B so both orders execute the same compiled
  sort function; this avoids the code-location artifact seen in the initial
  separate-function prototype.
- Routine 1k/10k/100k workloads, 3 warmups, median of 100 interleaved trials,
  three independent processes, correctness validation outside timers.

Latest unconditional descending-first median-of-three-process results at 100k:
- Random: -0.33%.
- Sorted: 0.00%.
- Reverse: -0.01%.
- Sorted+Noise(5%): -0.21%.
- Random%100: -0.91%.
- Alternating: -7.29%.
- Sawtooth: +0.04%.
- BlockSorted: -5.16%.
- OrganPipe: -0.39%.
- Rotated: +8.86%.
- Outside Rotated, all regressions are below the routine 2-3% significance band;
  Alternating and BlockSorted retain clear gains.

Mechanism check at 100k from the earlier instrumentation:
- Alternating: 2 runs. Descending-first exposed one ordered boundary and reduced
  measured merge comparisons from about 3 to 1.
- BlockSorted: about 10 runs. Merge comparisons fell about 19%.
- Rotated: exactly 3 runs. Ascending-first preserved an extremely cheap merge
  structure (about 7 measured merge comparisons); descending-first disrupted it
  and required about 45k comparisons.

Withdrawn selector work:
- An initial 2-or-[4,16] selector matched the routine suite but failed broader
  randomized sorted-block permutations: 4-5 run layouts often became much more
  expensive, and 6-9 remained mixed.
- A narrower 2-or-[10,32] selector avoided the Rotated regression and retained
  benchmark gains, but was withdrawn because the exact ranges are too specialized
  to justify as a general sorting policy across untested input families.

Decision:
- Retain always descending-game-first reconstruction in V2 because it is the
  simpler general rule and is neutral-to-faster on every routine family except
  Rotated, with meaningful wins on Alternating and BlockSorted.
- Accept the Rotated regression for now rather than encode input-specific run-count
  exceptions.
- Add one broad follow-up to the TODO: test descending-first for <=32 reconstructed
  piles/runs and ascending-first otherwise. This is intentionally a simple general
  threshold test motivated by the low-run Rotated failure mode, not a tailored

E053 — SIZE-AWARE FINAL PILE-DENSITY ROUTING
Date: 2026-08-08
Status: RETAINED
===============================================================================

Question:
- Is E052's normalized branchless-merge cutoff (final_piles^2 >= 7*n) stable
  across 10k, 100k, and 1M, or does the merge-kernel crossover itself move
  with problem size?

Forced-kernel scale audit:
- The crossover is NOT scale-invariant. Approximate observed normalized final
  pile densities and branchless/general behavior were:
    * n=10k: density ~5.9 was near parity; >=6.5 clearly favored branchless.
      Full Random density ~7.15 and branchless was ~11% faster.
    * n=100k: crossover occurred around density ~6.5-6.8. Full Random density
      ~7.61 and branchless was ~14% faster.
    * n=1M: density ~7.11 (Random-K=10k) still slightly favored general, while
      full Random density ~7.85 favored branchless by ~16%.
- Therefore one universal coefficient necessarily misroutes at least one size
  regime: 7*n is too conservative at 10k and too permissive for some 1M
  duplicate-heavy layouts.

Retained size-aware rule:
- For n <= 20k: branchless if final_piles^2 >= 6*n.
- For 20k < n < 500k: branchless if 4*final_piles^2 >= 27*n (~6.75*n).
- For n >= 500k: branchless if 2*final_piles^2 >= 15*n (~7.5*n).
- The first-64 earlyRandomLike requirement and eligible-type guards remain
  unchanged; this only refines the independent final-layout decision.

Direct size-aware versus universal-7 A/B:
- n=10k: large wins where universal 7 incorrectly stayed general, commonly
  ~5-8% and reaching ~15% in tested Random-K regimes; full Random was ~1%
  faster/near neutral because both policies are near the high-density end.
- n=100k: essentially neutral overall around the already-calibrated E052
  regime; targeted medium-cardinality cases showed small wins with no broad
  regression.
- n=1M: Random-K=10k improved ~6% because the size-aware rule correctly kept
  the general/galloping kernel; full Random remained on branchless and was
  effectively neutral apart from process noise.

Validation:
- Full maintained make test passed.

Interpretation / next router work:
- Final pile density is useful, but its optimal cutoff is size-dependent. This
  strengthens the two-stage design: early structure identifies insertion
  behavior, while final layout plus n chooses the merge kernel.
- Continue the multi-regime router by testing a cheap duplicate/saturation
  signal for INSERTION decisions; first-64 pile count alone cannot separate
  full Random from Random-K, while prefix distinctness can.

E055 — V2 NATURAL-RUN SCANNING / PIECEWISE-MONOTONE BATCHING PROTOTYPE
Date: 2026-08-08
===============================================================================

Goal
----
Test active Item 6: use source monotone runs to avoid repeated pile searches and
shape simulated piles more cheaply on structured inputs, while protecting Random.

Opportunity profile
-------------------
At n=100k over 30 seeds, profiling strict source runs >=4 elements found that
compatible whole-run-to-one-pile assignments are essentially nonexistent for
Random and Random%100, but materially present on structured inputs. Among
eligible run elements, compatibility was about 47.6% for Sorted+Noise(5%),
39.8% for BlockSorted, ~4.9% for Sawtooth, and ~100% for OrganPipe/Rotated.

Prototype
---------
For a detected strict monotone run, compare the first and terminal element's
destination against the current tail array. If both resolve to the same pile,
assign the entire run's blueprint tags at once, add the run length to that pile's
count, and update its tail to the terminal value. This preserves the simulated
representation without materializing physical piles. Incompatible runs fall back
to ordinary per-element insertion.

Result
------
A broad structured scanner was rejected. Sawtooth and some semi-structured cases
contain long source runs whose values span multiple patience piles, so scanning
them adds work without reducing searches. The promising sub-regime is strongly
piecewise-monotone input: prototypes repeatedly improved OrganPipe by roughly
16-19% and Rotated by roughly 21-28% at 100k. BlockSorted could also improve
substantially (~7-16%) with permissive scanning, but the gain was not robust once
miss-abandon guards were tightened. Random/Random%100 showed no useful long-run
opportunity.

Decision
--------
NO PRODUCTION CHANGE. Preserve the idea as a narrower piecewise-monotone router
branch. The next materially different test should classify a long compatible
continuation cheaply (for example, long initial prefix + next-run boundary
compatibility) before entering the run scanner, rather than scanning all
structured runs.

E056 - V1 STRUCTURED HINT MISS REFINEMENT AUDIT
Date: 2026-08-08
Status: rejected; no production sorting change.

Question:
- After E047's retained high-locality exact previous-pile hint, can a hint miss
  still be exploited cheaply by checking an adjacent pile, restricting the
  search direction, or changing the miss fallback from binary search to
  bit-walk?

Method:
- V1 only, 100k canonical/int workloads, same-binary runtime A/B.
- Retained E047 activation rule was preserved: non-Random-like first-64 prefix,
  >=4 total probe piles, >=16 usable hint observations, >=75% exact hint hits.
- Compared:
    A. retained exact-hint -> ordinary binary search on miss;
    B. one adjacent-pile check in the indicated direction -> bit-walk on miss;
    C. failed-hint direction -> binary search restricted to the correct half;
    D. exact-hint -> bit-walk on miss (control);
    E. adjacent check -> ordinary binary search on miss (control).
- Two independent seeds, 100 trials per family for the main comparison.
- Follow-up noise-prefix profiling used 5000 prefixes per noise level.

Main findings:
- The adjacent candidate initially appeared promising on Sorted+Noise(5%):
  ~5.1% and ~4.6% faster on the first two seeds.
- Control separation showed the adjacent check itself was not responsible:
  adjacent->binary was neutral, while exact-hint->bit-walk showed an even larger
  apparent gain (~6.7%) in the multi-mode experimental build.
- A clean outer dispatch was then tested so the >=85% locality decision was paid
  once after the probe rather than inside each miss. Under that cleaner layout,
  exact-hint->bit-walk was neutral-to-slower across the 0.5%-30% noise sweep;
  no robust whole-sort gain remained.
- Direction-restricted binary search also failed to produce a repeatable gain.
- Probe locality remains informative: mean exact hit rate was ~90.5% at 5%
  noise, ~85.1% at 7.5%, ~79.8% at 10%, with the existing >=75% route naturally
  deactivating as disorder rises. But no tested miss kernel improves on the
  retained ordinary binary fallback robustly enough to justify more routing.

Decision:
- Keep E047's exact previous-pile hint with ordinary binary-search fallback.
- Reject one-adjacent-pile and direction-restricted fallback kernels in their
  tested forms.
- Do not retain exact-hint->bit-walk fallback; its apparent gain was sensitive
  to experimental code layout and disappeared under a clean outer dispatch.
- Future V1 insertion work should move to materially different search kernels
  (especially SIMD/small-pile lookup) rather than further scalar miss-routing
  permutations.


E057 - V7 FIRST SIMD VARIATION: AVX2 EXACT-EIGHT PILE SEARCH
Date: 2026-08-08
Status: retained as experimental V7; V1-V6 unchanged.

Policy decision:
- SIMD work now receives separate variation numbers V7+ so scalar/general
  V1-V6 remain clean comparison baselines.
- V7 derives from canonical V2 ordinary simulated blueprint sorting.

Experiment:
- AVX2 int32 pile-tail lookup broadcasts the inserted value, compares against
  eight tails in one 256-bit register, converts the comparison to an 8-bit lane
  mask, and uses ctz to locate the insertion boundary. Generic types and custom
  comparators use the ordinary scalar search.
- Isolated lookup sweep compared scalar bit-walk to sequential AVX2 scans at
  pile counts 4..256. Exactly eight tails was the only clear SIMD win: about
  0.75-0.77x scalar lookup time (~23-25% faster). Four tails was slower, and
  12+ tails was substantially slower because scanning multiple vectors loses to
  logarithmic scalar search.
- A scalar-search-block + one-AVX-vector hybrid was also tested and rejected;
  its scalar block search/setup overhead made it slower for 12+ tails.
- Therefore V7 deliberately enables SIMD only when tails.size()==8.

Whole-sort causal A/B:
- To avoid attributing copied-header/code-placement effects to SIMD, V7 was
  compared against a layout-matched scalar clone, two independent seeds, 80
  trials, canonical generators. At 100k:
    * Random: V7/scalar 0.9949 and 0.9912 (~0.5-0.9% faster).
    * Random%100: 0.9918 and 0.9922 (~0.8% faster).
    * Other structured cases were mostly small/noisy; no broad structured claim
      is attributed to the exact-eight SIMD operation.
- Direct V2-vs-V7 timings show larger structured differences in some workloads,
  but those cannot be causally attributed to an operation that fires only at
  exactly eight tails; treat them as code-layout differences, not SIMD evidence.

Validation:
- 5000 randomized ascending + descending-comparator fuzz cases passed for V7.
- Full maintained make test suite passed.

Next:
- Before AVX-512, test probe-gated AVX2 small-pile continuation (E058).
- Also test non-linear SIMD search structures if proposed; do not extend V7 to
  sequential multi-register scans, which E057 rejected.

E058 - PROBE-GATED AVX2 SMALL-PILE CONTINUATION
Date: 2026-08-08
Status: rejected; V7 unchanged; no new production variation retained.

Question:
- Should AVX2 pile-tail lookup be treated primarily as an early/small-pile
  insertion optimization, with the first-64 probe deciding whether SIMD remains
  active after the probe, rather than allowing the V7 exact-eight specialization
  to fire anywhere in the full insertion?

Opportunity profile:
- At 100k, counting moments where the active game had exactly eight tails showed
  that full Random had only ~5 opportunities before element 64 and ~8 after it,
  while Random%100 had ~7 before / ~10 after. By contrast, structured low-pile
  cases can revisit or remain at eight tails much longer: Sawtooth ~4999
  post-probe opportunities and BlockSorted ~3750 in the simple pile-count
  profile. This supports using the probe to distinguish sustained-small-pile
  structure from high-growth Random before considering a continuation route.

Experiment:
- Built an experimental V2/V7-derived implementation in which AVX2 remained
  available during the first 64 processed values, then a single outer dispatch
  selected a SIMD-capable or scalar continuation from the probe pile count.
- Tested total-probe-pile ceilings 4, 8, 12, and 16. The active SIMD continuation
  still used AVX2 only at exactly eight tails; it never sequentially scanned
  multiple vectors.
- Initial separate-header comparisons again showed large structured movements
  caused by code layout, so those results were not treated as SIMD evidence.
- Repeated the test with a runtime SIMD on/off control inside the exact same
  compiled implementation so both sides shared code layout. Three independent
  seeds were used for the main 100k causal checks where completed.

Causal result:
- Probe-gated post-64 SIMD did not produce a stable advantage. With an 8-pile
  probe ceiling, mean SIMD/scalar ratios were approximately:
    Random 0.996, Random%100 0.999, Sorted+Noise5 0.996,
    Sawtooth 1.000, BlockSorted 1.000, OrganPipe 1.002,
    Rotated 1.005 (individual seeds fluctuated around parity).
- Changing the ceiling to 4 or 12 did not reveal a robust continuation regime;
  apparent structured gains in copied-header builds disappeared or became noisy
  under the same-code runtime control.
- A final probe-only isolation (SIMD permitted during the first 64 values and
  unconditionally disabled afterward) averaged roughly:
    Random 0.9956 (~0.4% faster), Random%100 0.9988,
    Sorted+Noise5 0.9955, Sawtooth 0.9996, BlockSorted 0.9988,
    OrganPipe 1.0038, Rotated 0.9981.
  The Random result was not stable enough across seeds (one ~1.4% win, other
  seeds near parity/slightly slower) to justify a production route.

Decision:
- Do NOT add a probe-gated AVX2 continuation variation.
- Keep V7 as the existing exact-eight experimental proof-of-concept.
- Treat E057's larger separate-header whole-sort movements cautiously: E058's
  same-code runtime control shows that the causal effect of exact-eight SIMD is
  very small at whole-sort scale.
- The user's architectural expectation is confirmed: once pile growth expands,
  AVX2 linear tail lookup should not be routed as a general post-probe search.
- The next SIMD family may test AVX-512 exact-sixteen lookup as its own V8, or a
  materially different SIMD search structure; do not revisit sequential AVX2
  multi-register scanning without a new algorithmic idea.

- Fixed 32 is already a strong broad compromise. No single larger fixed size is
  a general replacement.
- At 100k, Random has a shallow minimum around 128-256 (~0.3-0.5% gain) and
  Random%100 around 128 (~0.9% gain), but these gains are small.
- Larger bands progressively hurt Sawtooth, Rotated, and BlockSorted; at 10k the
  penalties become large. Their existing merge structure prefers many small
  deferred runs or has little overflow to amortize a large band sort.
- Size 16 is sometimes marginally useful on structured 10k cases, but hurts
  10k Random by ~4.8%.
- Therefore the useful next V5 work is NOT another global band constant. Proceed
  to post-insertion adaptive/nonuniform sizing and dynamic merge-tree balancing,
  using the actual frozen-run layout and overflow count to choose run boundaries.

E060 - V5 FIRST ADAPTIVE/NONUNIFORM RUN-SHAPING PASS
Date: 2026-08-08
Status: SIMPLE HEURISTICS REJECTED; TREE-AWARE BALANCING REMAINS OPEN

Goal
----
Move beyond E059's fixed band-size sweep and test whether cheap post-insertion
metadata can shape V5 overflow runs better than the fixed-32 baseline, including
a first bounded live pile-pair balancing experiment.

Method
------
- Canonical V5 insertion/freeze and final merge scheduler held fixed.
- n=100k, canonical generators, two independent seeds, 40 trials/seed.
- Same-binary rotated execution order; every output checked against std::sort.
- Adaptive overflow layouts tested:
    * by_run_count: nearest-power-of-two band size from overflow/frozen-run count,
      clamped to 16..1024;
    * by_median: nearest-power-of-two band size from median frozen-run length;
    * boundary_then32: if first overflow run pairs with the last frozen run,
      match that boundary run (bounded 16..1024), then return to 32;
    * boundary_then_adaptive: boundary match followed by adaptive run-count size.
- Separate live-balancing control: when the final two frozen runs pair on the
  first merge pass and the last run is smaller by <= 8/16/32 values, sort that
  many leading overflow values and merge them into the last frozen run before
  constructing the remaining fixed-32 overflow bands.

Adaptive sizing results
-----------------------
- Global metadata-derived sizing is not a general win. At 100k, run-count and
  median-derived sizes were roughly neutral on Random/Random%100 but regressed:
    Sawtooth ~10-11%, BlockSorted ~6-11%, Rotated ~8-14% across the two seeds.
- boundary_then32 was consistently far safer: generally within ~0.5% of fixed32,
  with occasional small structured wins (one Rotated seed ~2.6%). This indicates
  that the useful degrees of freedom are local merge boundaries, not a global
  replacement for 32.
- boundary_then_adaptive inherited the global-size regressions and is rejected.

Bounded last-pair top-up results
--------------------------------
- The simple "equalize a close pair" rule did not generalize.
- A 32-value cap occasionally helped (seed1 Sorted+Noise ~3.6%, Random%100 ~1.7%),
  but those gains did not repeat on seed2 and BlockSorted/OrganPipe could regress.
- 8/16-value caps likewise fluctuated around parity with workload-dependent wins
  and losses.
- Therefore local equality alone is not a sufficient objective. Equalizing two
  run lengths can add work without reducing merge depth or run count.

Decision
--------
- No V5 production change.
- Reject simple global adaptive band sizing and blind bounded pair equalization.
- KEEP the larger V5 idea open: overflow is a dynamic merge-tree balancing
  resource, but the router/planner must explicitly estimate the projected merge
  tree and compare saved merge depth/moves against the cost of sorting/inserting
  the consumed overflow fragment.
- Next V5 shaping attempt should simulate the actual adjacent merge schedule from
  run lengths and select overflow boundaries to reduce predicted total merge
  traffic/depth, rather than optimizing local run-size symmetry.

Date: 2026-08-08
Status: PROMISING SIGNAL, NOT RETAINED; CAUSAL VALIDATION INCONCLUSIVE

Goal

Test a richer final-layout route inside V2's Random-like branchless merge regime:
retain branchless merging for balanced adjacent run pairs, but use the ordinary

Experiment

- Same V2 insertion/reconstruction and E053 size-aware global branchless gate.

  galloping/general merging.
- Do not add a density-specific exception until a stricter merge-only or

E062 — V5 projected merge-tree shaping: power-of-two run counts + scheduler audit
Status: completed; no production code change retained.

Goal:
- Continue E060's V5 dynamic merge-tree balancing track with a planner that scores
  the actual downstream merge structure rather than merely equalizing neighboring
  run sizes.

Experiment A — power-of-two total-run planner:
- Baseline remained canonical V5 fixed-32 deferred overflow bands.
- Candidate repartitioned the same overflow so frozen_runs + overflow_runs fell to
  the largest feasible power-of-two run-count boundary below the fixed-32 baseline.
- Tested unconstrained and with 64/128/256 maximum deferred-band sizes.
- 100k, two seeds, canonical generators.

Result:
- No broad gain. Full Random and Random%100 were approximately neutral.
- Sorted+Noise and Sawtooth were typically ~0.5-1.8% slower.
- BlockSorted was ~1-3% slower.
- Rotated was unstable across seeds (one apparent win, one large loss).
- Rejected. The current adjacent-round merge plus ordered-boundary elimination does
  not behave like a simple textbook balanced tree where hitting a power-of-two run
  count automatically removes enough work to pay for larger deferred sorts.

Structural conclusion:
- Under the current adjacent-pair scheduler, changing sibling run sizes alone has
  limited leverage because most elements still participate once per merge level.
  Overflow shaping becomes substantially more meaningful only when it either
  changes run count/levels, enables boundary elimination, or is paired with a
  scheduler that actually uses run sizes.

Experiment B — scheduler audit on fixed-32 V5 runs:
- Compared V5's current defer_dominant_first_endpoint adjacent scheduler against
  generic selective PowerSort and always-PowerSort, with reconstruction/bands held
  fixed at 32.
- 100k, two seeds, canonical generators.

Representative ratios to current V5:
- Random: selective ~1.000; always PowerSort ~1.15 (large regression).
- Sorted+Noise(5%): selective/always ~1.08 (large regression).
- Random%100: approximately neutral to ~2% slower.
- Sawtooth: PowerSort ~1.7-3.1% faster.
- BlockSorted: ~0-2% faster depending seed.
- OrganPipe: approximately neutral.
- Rotated: highly seed/layout sensitive; one seed near neutral, one ~4-5% faster.

Decision:
- Do NOT globally couple V5 to PowerSort and do NOT retain the power-of-two run-count
  planner.
- Keep the broader V5 idea open: deferred overflow remains a dynamic merge-tree
  balancing resource, but future planners must route BOTH overflow partitioning and
  merge scheduler from actual post-insertion structure. A useful candidate must
  predict when a size-aware scheduler wins and then shape runs specifically for that
  scheduler; fixed adjacent merging cannot fully exploit arbitrary run-size shaping.

E066 — Benchmark methodology hardening after VM/std::sort drift audit
Status: methodology + benchmark-harness change; no sorting algorithm changed.

Why this was necessary:
- Repeated canonical runs showed that absolute std::sort medians can move enough
  between VM/host sessions to overlap the size of current JesseSort optimizations.
- E054 was later falsified by preserved-version recompilation: an apparently
  replicated 3-6% result came from harness/code-layout sensitivity rather than the
  intended mechanism. This demonstrated that 50-100 trial separate-run medians are
  no longer strong enough evidence for small retain/revert decisions.
- Saved absolute std::sort medians are therefore NOT a portable calibration constant.
  They are useful historical evidence only when the execution environment is known
  to be comparable. Same-run paired measurements are the primary evidence.

Canonical benchmark standard from E066 onward:
1. Default benchmark size remains n=100000 unless an experiment targets scale.
2. Default is TWO deterministic seeds (9100000 and 123456789).
3. Default is 500 timed trials PER SEED: 1000 paired observations per workload.
4. Claims below ~1.5% should use >=1000 trials per seed, or a phase-isolated causal
   harness with equal or stronger evidence.
5. Baseline/candidate/std::sort must run in the SAME executable/process whenever
   possible and receive the EXACT SAME source vector for each paired trial.
6. Execution order rotates every trial and reverses on alternating 8-trial blocks,
   distributing warm-cache, boost-clock, and order-position effects across methods.
7. Correctness validation remains OUTSIDE the timed region.
8. Short untimed warmups precede each input family.
9. Do not trim outliers by default. Preserve raw timings and report robust spread:
   median, p25, p75, IQR, and MAD.
10. Report BOTH:
    - ratio of aggregate medians, for continuity with historical tables; and
    - median of per-trial paired ratios, which is preferred for small same-run claims.
11. Preserve per-trial raw data so candidate effects can be reanalyzed without
    rerunning and so order/seed sensitivity can be inspected.
12. Emit per-seed summaries in addition to pooled summaries. A retained small gain
    should not depend on one seed unless the mechanism is explicitly seed/data-shape
    specific.
13. For important micro-optimizations, prefer phase-isolated/layout-matched causal
    harnesses in addition to whole-sort timing.
14. Cross-run absolute timing comparisons are secondary evidence. Preserved-version
    recompilation in one current harness is preferred when auditing regressions.

benchmark.cpp changes:
- Default changed from 30 trials/one implicit seed to 500 trials/seed x 2 seeds.
- Canonical seeds standardized to 9100000 and 123456789.
- Same-input paired trial records added.
- Balanced rotating/reversing execution order added.
- Two untimed warmup trials/input by default.
- benchmark_results.csv changed to long-form robust summaries with median, quartiles,
  IQR, MAD, ratio-of-medians, and paired-ratio quartiles.
- benchmark_trials.csv added with every raw time, std::sort partner time, paired ratio,
  seed, trial number, and execution-order position.
- benchmark_metadata.txt added with trial configuration, compiler, CPU model when
  available, hardware concurrency, AVX2 compile status, timestamp, and a warning that
  absolute medians are not portable across VM sessions.
- Per-seed and pooled summaries are both emitted.

Interpretation policy:
- For a candidate-vs-baseline optimization experiment, the most persuasive number is
  the paired candidate/baseline distribution from a same-binary harness, not two
  independently measured medians from different builds/runs.
- std::sort ratios remain useful for external competitiveness, but they should be
  computed from std::sort timings collected in that SAME benchmark run.
- Historical std::sort ratios should not by themselves trigger a retain/revert decision.

E070 — Isolated/checkpointed benchmark artifacts + native build standard
Status: benchmark infrastructure only; no sorting algorithm changed.

Motivation:
- Long benchmark tool/terminal calls can time out even when the benchmark process has
  started or completed useful work. Results must survive loss of the interactive response.
- Old benchmark artifacts must never be accidentally consumed by a later timing summary.
- Benchmark builds should use the intended local CPU target while comparing JesseSort and
  std::sort in the same binary; the canonical Makefile benchmark build now uses
  `-O3 -march=native -DNDEBUG` instead of globally forcing only `-mavx2`.

Artifact isolation/checkpoint policy:
1. Every benchmark invocation creates a unique `results/run_YYYYMMDD_HHMMSS[_N]/` directory.
2. The benchmark NEVER reads prior run directories when computing a current summary.
3. `benchmark_trials.csv` is appended for each completed paired trial and flushed every
   10 trials (and at each seed boundary/end), so raw timing evidence survives ordinary
   terminal/tool response timeouts.
4. `benchmark_results.csv` contains only the current invocation and is flushed after every
   completed workload; a timeout therefore leaves summaries for all completed workloads.
5. `benchmark_progress.txt` is rewritten during the run with the active input, seed, trial,
   and state, allowing partial-run recovery/diagnosis.
6. `benchmark_metadata.txt` is written at startup in the same run directory.
7. `/results/` is gitignored. Generated timing artifacts are intentionally ephemeral and
   should be exported/shared as needed, then removed with `make clean-results`.
8. No top-level packaged benchmark-result snapshot is retained; this avoids stale results
   being mistaken for current evidence.

Makefile targets:
- `make bench200`: 200 trials, one seed, n=100000 (exploratory only).
- `make bench500` / `make run`: canonical 500 trials/seed x 2 seeds, n=100000.
- `make bench1000`: 1000 trials/seed x 2 seeds for small effects.
- `make clean-results`: deletes the entire ignored results tree.

This E070 policy supplements E066; E066 remains the statistical methodology standard.
